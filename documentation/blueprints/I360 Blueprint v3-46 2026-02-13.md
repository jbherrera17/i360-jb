## Phase 54l: Platform Admin Auth & User Creation Enhancements (v3.46)

### What Was Completed

Resolved a critical gap where users added to the `platform_admins` table could not access the Administrator dashboard or admin API endpoints because the auth system only checked the `users.role` column. The login and `/me` endpoints now query the `platform_admins` table and return `is_platform_admin` status. Navigation and middleware use this to grant admin access. The Add User form was redesigned so platform admin status and organization assignment are independent selections rather than mutually exclusive.

### Enhancements

| Enhancement | File(s) | Description |
|-------------|---------|-------------|
| **Login returns platform admin status** | `server/routes/auth.js` | `POST /api/auth/login` queries `platform_admins` table; returns `is_platform_admin` and `platform_admin_role` in response |
| **`/me` returns platform admin status** | `server/routes/auth.js` | `GET /api/auth/me` checks `platform_admins` table; `is_admin` now true for either `role=admin` OR platform admin |
| **`requireAdmin` recognizes platform admins** | `server/routes/auth.js` | Middleware now checks `platform_admins` table when `profile.role !== 'admin'`, granting admin API access to platform admins |
| **Navigation shows Administrator** | `public/js/navigation.js` | New `isCurrentUserAdmin()` checks both `role` and `is_platform_admin`; admin nav group and user menu updated |
| **Role label shows "Platform Admin"** | `public/js/navigation.js` | User menu displays "Platform Admin" instead of "User" for platform admins |
| **Independent assignment sections** | `public/admin.html` | Add User form: platform admin checkbox with role selector + always-visible org assignment with org/role selects |
| **Dual assignment on create** | `public/admin.html` | `handleSaveUser()` processes platform admin and org assignment independently via `updateUserAssignments()` |

### Files Modified

| File | Changes |
|------|---------|
| `server/routes/auth.js` | Platform admin lookup in login, `/me`, and `requireAdmin` middleware |
| `public/js/navigation.js` | `isCurrentUserAdmin()` helper, admin group filter, user menu updates |
| `public/admin.html` | Redesigned `buildNewUserAssignment()`, updated `toggleNewPlatformFields()`, updated `handleSaveUser()` |

## Phase 54k: User Management & Data Loading Fixes (v3.45)

### What Was Completed

Fixed critical bugs in user management where business role and department were not persisted when creating users, and the edit modal was using an incomplete data source. Improved data loading resilience so partial API failures no longer block the entire UI.

### Bug Fixes

| Fix | File(s) | Description |
|-----|---------|-------------|
| **Business role/dept not saved on create** | `server/routes/auth.js` | `POST /api/auth/users` was ignoring `business_role` and `department_id` from request body — now included in profile upsert |
| **Edit modal using wrong data source** | `public/admin.html` | `openEditModal()` used basic `users` array; now uses `unifiedUsers` (with assignments data) with fallback |
| **Hardcoded business role options** | `public/admin.html` | New `buildBusinessRoleOptions()` dynamically generates select options from `businessRoles` API data |
| **`populateDepartmentDropdown` crash** | `public/admin.html` | Function crashed on every `loadData()` call because `#userDepartment` only exists inside modal; added null safety |
| **`loadData` fails on partial errors** | `public/admin.html` | Changed `Promise.all` to `Promise.allSettled` so individual fetch failures don't block rendering |
| **Assignment refresh stale data** | `public/admin.html` | `addPlatformAdmin`, `removePlatformAdmin`, `addOrgMembership`, `removeOrgMembership` now use `openEditModal()` directly after `loadData()` |

### Files Modified

| File | Changes |
|------|---------|
| `server/routes/auth.js` | Extract `business_role` and `department_id` from request body; include in user profile upsert |
| `public/admin.html` | Dynamic business role options, unified user data source, resilient data loading, null-safe DOM access |

## Phase 54j: Onboarding & Setup Flow Overhaul (v3.44)

### What Was Completed

Redesigned the organization onboarding experience following a two-phase pattern: wizard-based setup for platform admins and checklist-based onboarding for client admins. The setup wizard now guides through 8 comprehensive steps including soul config templates and module access. The onboarding checklist groups items by priority with live auto-detection. Agent categories migrated from emoji to Lucide icons. The Administrator dashboard was reorganized to consolidate all management cards under Platform Administration.

### Setup Wizard Expansion (5 → 8 Steps)

| Step | Title | Type | Description |
|------|-------|------|-------------|
| 1 | Organization Details | Required | Name, slug, description, industry |
| 2 | Subscription Tier | Required | Tier selection with resource limits preview |
| 3 | Admin User | Required | Admin account configuration |
| 4 | Soul Config Template | Required | 6 industry templates (SaaS, Healthcare, Legal, Finance, Nonprofit, Agency) with values, bright lines, and voice |
| 5 | Module Access | Required | 17 platform modules with tier-gated availability, toggle on/off |
| 6 | Departments | Optional | Department creation with skip option |
| 7 | Starter Resources | Optional | Seed agents and context asset templates |
| 8 | Review & Complete | Required | Summary of all selections with edit links |

| Priority | Items | "Ready" Threshold |
|----------|-------|-------------------|
